## 맥락
- React + Vite 확정(PRD v2). 시연 URL 1개, 계정 2종 역할 분기(M-14), 폴링 5~10s(WBS D10).
- 기능명세서(2026-07-19) 3화면 체계: SCR-01 위험지도 / SCR-02 우선순위 리스트 / SCR-03 순찰 대상 상세.
- 사용자 최우선 축: 빠른 지도·현재 위치 실시간성(단말 자기 위치 표시 범위), 부가 길찾기.
- 도농 전환은 토글이 아니라 지역 선택(FR-001)에 따른 `region_type` 자동 결정 (기능명세서 정본).

## 검토한 선택지
- 라우팅: **단일 앱 + 역할 라우트 분리(채택)** vs 앱 2개 분리 배포(URL 1개 확정사항과 충돌 — 기각)

## 결정
1. **라우팅 (확정, v1.1 개정):** 단일 React 앱. ~~`/login` → 계정 2종 역할 분기~~ → **로그인 후 기본 `/control`(SCR-01 지도 + SCR-02 리스트), 관제 화면의 '현장모드로 전환' 버튼으로 `/field`(SCR-02 명단 + SCR-03 상세 회신) 진입, 현장 드로어의 '현장점검 종료'로 `/control` 복귀.** 계정 2종 역할 분기는 폐기(단일 계정·인앱 전환). ~~`/field`만 모바일 우선 반응형~~ → **(v1.2) 관제·현장 공통 검증 기준 = 태블릿 1024×768 가로.** 데스크톱 ≥1280은 여유 폭 활용(관제 큐 패널 확장), 모바일 375는 깨지지-않음 best-effort. **(v1.3) 진입점 `/login` 복원** — v1.1에서 폐기한 것은 "`/login`에서 계정 2종으로 역할을 가르는 모델"이지 로그인 화면 자체가 아니었다. 단일 계정·인앱 모드 전환 원칙은 그대로 두고, `/` → `/login` → (로그인) → `/control` 순서만 복원한다. 함께 `/signup`(아이디·비밀번호·이름·전화번호·생년월일)과 `/settings`(계정 조회·네이버 지도 유형·로그아웃/회원탈퇴)를 신설. **라우트 가드는 두지 않는다** — 인증 백엔드가 없고(ADR-005에 인증 엔드포인트 미정의) 시연 중 `/control` 직접 진입이 필요하다. 로그인·회원가입은 전부 목업이며 **비밀번호는 어떤 형태로도 저장하지 않는다**. 실제 인증 계약은 백엔드 착수 시 ADR-005에 추가한다.
2. **지도 (확정, v1.2 개정 / v1.6 실장 완료):** ~~react-leaflet + `preferCanvas: true` 제안~~ → **Naver Maps API 채택.** 현재 위치 버튼·핀 포커스 훅 등 FE 준비 코드와 일치. GeoJSON 경량화(좌표 5자리·시군구 클리핑)는 pipeline 책임 유지, 현재 위치는 단말 위치 마커.
   - **(v1.5) `@types/navermaps` 도입** (types-only devDependency, 런타임 0). 손으로 쓴 선언을 쓰다가
     실제로 물렸다 — 공식 문서가 클릭 리스너를 `addEventListener`로 설명하는데 런타임에는 `addListener`만
     있었고, **직접 쓴 선언은 틀려도 컴파일러가 잡아주지 않는다.** 도입 즉시 `addGeoJson` 인자 수,
     `revertStyle` 시그니처, `MapTypeId`가 소문자 리터럴이라는 것 등 5건이 잡혔다.
   - **(v1.5) 핀 렌더는 가시 영역 한정.** 격자 하나에 최대 975건·관악구 22,501건이라 전량 마커는 불가능하다.
     클러스터링(`MarkerClustering.js`)은 코어 SDK에 없어 파일 벤더링이 필요한데, 격자로 드릴다운한 뒤라
     한 화면이 수백 건 수준이고 큐도 `size=100`으로 끊겨 온다 — 의존성 0으로 충분하다.
   - **(v1.5) 등급 라벨·점수는 선택 시 말풍선으로 병기.** DESIGN.md의 "핀 옆 **또는 말풍선**" 중 후자다.
     밀집 지역에서 모든 핀에 라벨을 붙이면 라벨끼리 겹쳐 아무것도 읽히지 않는다 — 병기를 없앤 게 아니라
     읽히는 시점으로 옮겼다.
   - **(v1.6) 지도 유형·줌·현재 위치·거리순까지 연결 완료.** `/settings`의 `MAP_TYPE`은 Naver Maps `mapTypeId`와 1:1이고,
     B2 거리순은 단말 위치가 잡힌 뒤 현재 위치에서 격자 중심까지의 직선거리로 정렬한다.
   - **격자 위험 밀집 표시 방식은 여전히 미결.** 지도는 "옅은 실선 경계"까지만이고 코로플레스는 열려 있다.
3. **서버 상태 (확정, v1.4 개정):** ~~TanStack Query, `refetchInterval` 7s, 저장 후 invalidate~~ →
   **직접 만든 조회 훅 `useApiQuery` 채택, 의존성 추가 없음.**
   - 근거: 쿼리가 6종이고 대부분 화면 진입 시 1회 조회라 캐시·무효화 계층이 하는 일이 없다.
     손으로 만들 때 실제로 틀리는 둘(**응답 경합** — 동을 빠르게 바꾸면 늦게 온 응답이 화면을 되돌림,
     **재조회 깜빡임** — 목록이 비었다 다시 참)만 훅 한 곳에서 처리한다.
   - 폴링(`refetchInterval`)은 **채택하지 않는다.** 갱신은 새로고침 버튼과 화면 재진입으로만 일어난다
     (DESIGN.md "큐는 고정 목록"과 같은 결론). 폴링이 필요해지면 훅에 인터벌을 더하면 된다.
   - Redux/Zustand 반려는 그대로. 서버에서 온 것은 훅이, 화면 로컬 상태는 `useState`가 든다.
   - 뒤집을 조건: 저장 후 큐 갱신(M-12 피드백 루프)이나 화면 간 캐시 공유가 필요해지면 재검토한다.
4. 이하 **보류 (추후 결정)** — 제안안 기록:
   - 차트: 라이브러리 미도입 — 집계 카운터는 숫자 카드로.
   - 길찾기: 카카오맵/티맵 딥링크(외부 API 의존 0 유지).

## 근거
- URL 1개·컴포넌트 재사용·기능명세서 3화면의 자연 배치.

## 결과 (트레이드오프 수용)
- ~~§3 보류(폴링·차트·길찾기)로 FE 착수 시점(WBS 1주차)에 재결정 필요~~ → **(v1.4) 서버 상태는 확정됐고 폴링은 채택하지 않았다.** 남은 보류는 차트·길찾기 둘뿐이며 화면이 미구현이라 급하지 않다.
- **(v1.4) 캐시가 없어 화면 간 같은 조회가 반복된다** — 지역 사전은 37행, 격자 GeoJSON은 `Cache-Control: max-age=86400`이라 실측 응답이 9~37ms다. 이 비용을 수용한다.
- **(v1.6) 지도는 실장 완료.** `MapPlaceholder`는 실제 Naver Maps 캔버스로 교체됐고, 남은 지도계 보류는 격자 위험 밀집 표시 방식과 길찾기 딥링크뿐이다.
- **(v1.7) 길찾기 실장.** 웹 URL을 새 탭으로 연다. 앱 스킴은 앱이 없을 때 조용히 실패해 "눌러도 반응 없는 버튼"이 되므로 쓰지 않는다 — 그 버튼이 원래 그랬고 그걸 고치는 중이었다. 딥링크는 URL 규약이라 키·SDK·네트워크 호출이 없어 §2의 "외부 API 의존 0"은 유지된다. **남은 보류는 차트 하나다.**
- **(v1.8) 길찾기를 네이버 지도로 교체.** 원래 이 항목은 지도 스택이 확정되기 전에 "카카오맵/티맵"으로 적혀 있었고 v1.7이 그대로 실장했으나, **화면은 Naver Maps인데 길찾기만 다른 서비스로 튀는 것이 일관되지 않아** 되돌렸다. `https://map.naver.com/p/directions/-/{lng},{lat},{name}/-/car`이며 **좌표가 경도,위도 순서**다(카카오와 반대).

  **수용한 손해:** 네이버가 공식 문서화한 길찾기 연동은 `nmap://route/*` 앱 스킴뿐이고 **웹 폴백이 문서에 없다.** 우리가 쓰는 웹 URL은 네이버 지도 웹앱의 내부 주소라 예고 없이 바뀔 수 있다 — 카카오의 `link/to`가 공식 규약이었던 것과 다른 점이며, 일관성을 얻는 대신 내준 것이다. 길찾기가 엉뚱한 화면을 열면 `lib/map-link.ts`부터 본다.
